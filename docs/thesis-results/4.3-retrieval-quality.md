# 4.3 คุณภาพการดึงข้อมูล (RAG Retrieval Quality)

> เอกสารร่างสำหรับบทที่ 4 ของวิทยานิพนธ์ — เนื้อหาภาษาไทยพร้อมตารางที่คัดลอกไป
> Word/Google Docs ได้ทันที ตัวเลขทั้งหมดมาจากผลรันจริง อ้างอิง artifact ท้ายเอกสาร

## 4.3.1 การออกแบบการทดลอง

การทดสอบนี้วัดคุณภาพของขั้นตอน **retrieval** (การดึงเอกสารที่เกี่ยวข้อง
จากคลังความรู้) ซึ่งเป็นรากฐานของระบบ RAG — ถ้า retrieval ดึงเอกสารผิด
แม้ตัวสร้างคำตอบ (generator) ดีแค่ไหน คำตอบสุดท้ายก็ไม่มีทางถูกต้อง

**คลังความรู้ (Knowledge Base)**

| องค์ประกอบ | รายละเอียด |
|---|---|
| จำนวนไฟล์ | 24 ไฟล์ (Markdown 18 + PDF 6) |
| แหล่งเนื้อหา | คู่มือกรมสรรพากร (PIT90), คู่มือลงทุน, ตำราการเงินการพฤติ (เช่น Ritter, EH&H Lifelong) และเอกสารที่เขียนถ่วงน้ำหนักจากแหล่งอ้างอิงทางการ |
| ขนาด chunk | 500 ตัวอักษร, เหลื่อมกัน (overlap) 50 ตัวอักษร |
| จำนวน chunks หลังแบ่ง | 1,586 chunks |

**โมเดลและพารามิเตอร์**

| พารามิเตอร์ | ค่า |
|---|---|
| Embedding model | `models/gemini-embedding-001` (Google) |
| Vector store | ChromaDB (เก็บถาวรที่ `data/chroma_db`) |
| Top-k | 3 ผลลัพธ์ต่อหนึ่ง query |
| Domain filter | กรองตามโดเมนของ query (tax / expense / investment / general) |

ข้อสังเกต: การทดสอบนี้วัดเฉพาะขั้น retrieval จึงไม่มีการเรียกโมเดลสนทนา
(LLM) ใด ๆ ตัวแปรที่วัดจึงสะท้อนคุณภาพของ embedding + chunking +
vector search เพียว ๆ

**ชุดทดสอบ (Dataset v1.1)** — 39 queries ภาษาไทย/ผสมอังกฤษ ที่คัดเลือก
ให้ครอบคลุมกรณีขอบเขต (boundary) ของแต่ละโดเมน พร้อมกำกับไฟล์ต้นทาง
ที่ "ควร" ถูกดึง (`expected_source_files`) และคำสำคัญที่ต้องปรากฏในเนื้อหา
ที่ดึงได้ (`expected_keywords`) โดยทุกคำสำคัญได้รับการตรวจสอบยืนยันกับ
เนื้อหาจริงในไฟล์แล้ว

| โดเมน | จำนวน query |
|---|---|
| tax (ภาษี) | 13 |
| general (การเงินทั่วไป) | 12 |
| investment (การลงทุน) | 11 |
| expense (รายจ่าย/งบประมาณ) | 3 |
| **รวม** | **39** |

**ตัวชี้วัด** — Recall@3 (สัดส่วนไฟล์ที่ควรดึงและถูกดึงมาแล้ว),
Precision@3 (สัดส่วนช่องผลลัพธ์ที่ถูกต้อง), MRR (Mean Reciprocal Rank —
ตำแหน่งของไฟล์ที่ถูกต้องอันดับแรก), และ Keyword Hit Rate (สัดส่วน
คำสำคัญที่คาดหวังซึ่งปรากฏในเนื้อหาที่ดึงมา) เมื่อดึงซ้ำหลาย chunks
จากไฟล์เดียวกัน จะนับเป็นไฟล์เดียว (deduplicated)

## 4.3.2 ผลลัพธ์ภาพรวม

รันเมื่อ 2026-09-22 บน index ที่สร้างใหม่ทั้งหมด (one-shot indexing ของ
24 ไฟล์ → 1,586 chunks) ได้ผลดังนี้

| ตัวชี้วัด | ค่า | คำอธิบาย |
|---|---|---|
| Recall@3 | **0.897** | ค้นพบไฟล์ที่ควรดึงครบ 35 ใน 39 queries |
| MRR | **0.808** | ไฟล์ที่ถูกต้องมักอยู่อันดับ 1 |
| Keyword Hit Rate | **0.910** | เนื้อหาที่ดึงมามีคำสำคัญที่คาดหวังเกือบครบถ้วน |
| Precision@3 | 0.299 | นับตาม "ช่องผลลัพธ์" ทั้ง 3 ช่อง (ดูคำอธิบาย 4.3.4) |
| Distinct-source Precision | 0.624 | นับเฉพาะไฟล์ที่ไม่ซ้ำกัน |
| Latency เฉลี่ย | 589 ms/query | รวม embedding ของ query + vector search |

## 4.3.3 ผลลัพธ์แยกตามโดเมน

| โดเมน | n | Recall@3 | MRR | Keyword Hit | Precision@3 |
|---|---|---|---|---|---|
| expense | 3 | 1.000 | 1.000 | 1.000 | 0.333 |
| investment | 11 | 1.000 | 0.955 | 0.955 | 0.333 |
| general | 12 | 0.917 | 0.875 | 0.917 | 0.306 |
| tax | 13 | 0.769 | 0.577 | 0.846 | 0.256 |
| **รวม** | **39** | **0.897** | **0.808** | **0.910** | **0.299** |

โดเมน investment (รวมกลุ่มสินทรัพย์ดิจิทัลที่เพิ่มเข้ามา) และ expense
ได้คะแนนเต็ม — ทุก query ดึงไฟล์ที่คาดหวังครบถ้วน ส่วน tax ต่ำที่สุด
ซึ่งวิเคราะห์รายกรณีไว้ในหัวข้อถัดไป

## 4.3.4 การวิเคราะห์ผล

### (ก) กรณีที่ไม่พบไฟล์ที่คาดหวังเลย (4 ใน 39 queries)

| Case | Query (ย่อ) | ไฟล์ที่คาดหวัง | ไฟล์ที่ดึงได้จริง | Keyword hit |
|---|---|---|---|---|
| rag_002 | อัตราภาษีเงินได้บุคคลธรรมดา | tax_thai_personal_income.md | tax_personal_income_guide.pdf, tax_pit90_guide_2568.pdf | **1.00** |
| rag_008 | กฎเกณฑ์การยื่นภาษีประจำปี | tax_thai_personal_income.md | tax_filing_guide.md, tax_pit90_guide_2568.pdf | 0.50 |
| rag_026 | behavioral bias ที่มีผลต่อการตัดสินใจทางการเงิน | finance_behavioral_reasoning_chains.pdf | finance_behavioral_finance_ritter.pdf, debt_psychology_payoff.md | **1.00** |
| rag_033 | หุ้นปันผล ถูกหักภาษี ณ ที่จ่ายแล้วต้องนำไปรวมคำนวณไหม | tax_vat_withholding.md | tax_pit90_guide_2568.pdf | 0.50 |

การวิเคราะห์พบว่ากรณีพลาดทั้ง 4 **ไม่ใช่การดึงเอกสารผิดเนื้อหา
แต่เป็นการดึง "เอกสารที่ถูกต้องอีกฉบับ"**:

1. **rag_002 และ rag_026** มี Keyword Hit Rate เต็ม 1.00 กล่าวคือ
   เนื้อหาที่ดึงมามีคำสำคัญครบทุกคำที่คาดหวัง แต่มาจากไฟล์อื่นในหัวข้อ
   เดียวกัน (เช่น คู่มือ PIT90 ของกรมสรรพากร แทนไฟล์สรุปที่ annotate ไว้)
   นี่คือข้อจำกัดของ **ความเข้มงวดของ ground truth** มากกว่าความผิดพลาด
   ของระบบ — ในความเป็นจริงคู่มือฉบับทางการน่าจะเป็นแหล่งอ้างอิงที่ดีกว่าด้วยซ้ำ
2. **rag_008** ("กฎเกณฑ์การยื่นภาษี") ระบบดึง `tax_filing_guide.md`
   ซึ่งชื่อและเนื้อหาสอดคล้องกับ query โดยตรง แต่ dataset กำกับให้
   expected เป็นไฟล์สรุปภาษีรวม — จุดนี้ชี้ว่า annotation ควรปรับให้
  ยอมรับหลายไฟล์ (multi-label)
3. **rag_033** เป็นกรณีเดียวที่ถือว่า miss อย่างแท้จริงในเชิงเนื้อหา
   (คำถามเรื่องภาษีหัก ณ ที่จ่ายสำหรับหุ้นปันผล แต่ระบบดึงคู่มือ
   PIT90 ทั่วไปซ้ำทั้ง 3 ช่อง) อย่างไรก็ตามคู่มือ PIT90 ก็มีหัวข้อ
   เกี่ยวกับการนับรวมเงินได้จากการหัก ณ ที่จ่ายอยู่จริง จึงเป็น
   "ผลลัพธ์รอง" ที่ยังใช้ประกอบคำตอบได้

สรุปได้ว่า Recall ที่แท้จริงในเชิงเนื้อหา (content-level) น่าจะสูงกว่า
0.897 อย่างมีนัยสำคัญ แต่เพื่อความอนุรักษ์นิยม รายงานตามตัวเลข
เชิงไฟล์ (file-level) ตามตาราง

### (ข) การแปลผล Precision@3 ที่ต่ำ

Precision@3 = 0.299 ดูต่ำเมื่อเทียบกับ Recall ที่ 0.897 แต่เป็น
**คุณลักษณะเชิงโครงสร้างของระบบ ไม่ใช่ความผิดพลาด** เนื่องจากการค้นหา
คืนผลลัพธ์เป็น "chunk" ไม่ใช่ "ไฟล์" คำถามหนึ่งข้อมักได้ 3 chunks
มาจากไฟล์เดียวกัน (พบ 23 ใน 39 queries ที่ดึงหลายไฟล์ และส่วนใหญ่
ที่เหลือดึงไฟล์เดียวทั้ง 3 ช่อง) เมื่อไฟล์ที่คาดหวังมีเพียง 1 ไฟล์
ค่าสูงสุดของ Precision@3 จึงถูกกดไว้ที่ ~1/3 โดยธรรมชาติ

ตัวชี้วัดที่สะท้อนคุณภาพได้ตรงกว่าคือ **Distinct-source Precision**
(นับเฉพาะไฟล์ไม่ซ้ำ: ไฟล์ที่ถูกต้อง ÷ จำนวนไฟล์ที่ต่างกันที่ดึงมา)
ซึ่งได้ **0.624** และเมื่อพิจารณาว่าการดึงหลาย chunks จากไฟล์ที่ถูกต้อง
เป็นพฤติกรรมที่พึงประสงค์ (ตอบได้ละเอียดขึ้น) แนวทางปรับปรุงคือ
ทำ **source-level re-ranking** คือดึง top-k แล้วกระจายผลลัพธ์ให้
มาจากหลายไฟล์ (MMR / maximal marginal relevance) ซึ่งบันทึกไว้เป็น
future work

### (ค) โดเมนภาษีต่ำที่สุด

โดเมน tax มี Recall 0.769 และ MRR 0.577 ต่ำที่สุดชัดเจน สาเหตุหลัก
คือคลังความรู้ฝั่งภาษีมีเอกสาร**ซ้อนทับกันมาก** (คู่มือกรมสรรพากร
PDF หลายฉบับ + ไฟล์สรุป Markdown ในหัวข้อเดียวกัน) ทำให้แต่ละ query
มี "คำตอบที่ถูกต้องได้หลายฉบับ" การวัดแบบ single-label จึงลงโทษ
กรณีที่ระบบเลือกฉบับทางการแทนไฟล์ที่ annotate ไว้ ดังกรณี (ก)
ข้างต้นทั้งหมดเป็นคำถามโดเมนภาษี

### (ง) ตรวจสอบความถูกต้องของเครื่องมือวัด (evaluation harness QA)

ระหว่างการรันครั้งแรกของการทดสอบนี้ ผู้วิจัยพบว่าค่า Recall มีค่า
สูงกว่า 1.0 (2.0–3.0) ใน 31 จาก 39 queries ซึ่งเป็นค่าที่เป็นไปไม่ได้
การไล่หาสาเหตุพบว่าตัวชี้วัดเดิมนับ chunks ที่ซ้ำกันแยกกัน (ไฟล์เดียว
ถูกดึง 3 ช่อง และเป็นไฟล์ที่คาดหวัง จึงได้ hits = 3) ผู้วิจัยแก้ไขด้วย
การนับ source แบบไม่ซ้ำ (deduplicate) ทั้งใน Recall และ Precision
พร้อมเพิ่ม regression tests 3 กรณี แล้วรันการประเมินซ้ำบน index เดิม
(ไม่มีการ re-embed เอกสาร) ตัวเลขทั้งหมดในเอกสารนี้จึงผ่านการตรวจ
สอบว่าอยู่ในช่วง [0, 1] ครบทุกกรณี — สะท้อนการควบคุมคุณภาพของ
เครื่องมือวัดก่อนนำผลไปอ้างอิงจริง

## 4.3.5 สรุป

- ระบบ retrieval ดึงไฟล์ต้นทางที่คาดหวังครบถ้วน **89.7%** ของ queries
  และไฟล์ที่ถูกต้องส่วนใหญ่อยู่อันดับแรก (MRR 0.808)
- คำสำคัญที่จำเป็นปรากฏในเนื้อหาที่ดึงมา **91.0%** — สนับสนุนว่า
  ขั้นตอน grounding ของ LLM จะได้วัสดุที่ถูกต้องเพียงพอ
- กรณีพลาดทั้ง 4 ส่วนใหญ่เกิดจากความเข้มงวดของ ground truth
  (single-file annotation ในโดเมนที่เอกสารซ้อนทับสูง) มากกว่าความ
  ผิดพลาดของการดึงข้อมูลเชิงเนื้อหา
- แนวทางปรับปรุง: (1) ปรับ dataset เป็น multi-label expected files
  (2) source-level re-ranking ด้วย MMR (3) เพิ่มกรณีทดสอบโดเมน
  expense ซึ่งปัจจุบันมีเพียง 3 queries
