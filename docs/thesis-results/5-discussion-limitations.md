# บทที่ 5 สรุปผล อภิปราย และข้อจำกัดของงาน

> เอกสารร่างสำหรับบทที่ 5 ของวิทยานิพนธ์ — สังเคราะห์จากผลการ
> ประเมินในบทที่ 4 (4.1–4.4) ตัวเลขทั้งหมดอ้างอิงรายงานร่าง
> `docs/thesis-results/` และ artifact การรันจริง

## 5.1 สรุปผลการประเมินเชิงระบบ

ระบบ Personal Finance AI ที่พัฒนาขึ้นเป็นระบบ multi-agent LLM
แบบ Hub-and-Spoke (Router + 6 specialist agents) พร้อม RAG
ความรู้ภาษาไทย 24 เอกสาร ผลการประเมินภาพรวม:

| มิติ | ตัวชี้วัด | ผลลัพธ์ | บท |
|---|---|---|---|
| การจำแนกเจตนา (single-turn) | accuracy | **0.943** | 4.1 |
| การจำแนกเจตนา (multi-turn) | accuracy | **1.000** (base 0.733) | 4.1 |
| ความถูกต้องคำนวณภาษี | within tolerance | **95%** (MAE 3,000 THB) | 4.2 |
| ความสมเหตุสมผล (hallucination) | คำตอบหลักตรง KB | **10/10** | 4.2 |
| การค้นคืนความรู้ (RAG) | Recall@3 / MRR | **0.897 / 0.808** | 4.3 |
| ต้นทุนโครงสร้าง routing | LLM calls / query | **1.0** (P2P 1.8, Hier 2.0) | 4.4 |

จุดเด่นเชิงประจักษ์ 3 ประการ:

1. **Router ที่พัฒนาต่อจนแก้จุดอ่อนจริงได้** — ใน multi-turn
   ที่ข้อความกำกวมจนแก้ไม่ได้เชิงตรรกะถ้าไม่มีบริบท accuracy
   กระโดดจาก 0.733 → 0.933 และ 1.000 ใน configuration สมบูรณ์
2. **การคำนวณการเงินที่ปลอดภัยด้วยเครื่องมือ** — ความถูกต้องภาษี
   95% มาจากการให้ agent เรียก tax calculator (deterministic)
   แทนการคิดเลขเองด้วย LLM ทำให้ข้อผิดพลาดเชิงตัวเลขไม่แพร่
3. **สถาปัตยกรรมที่เลือกด้วยหลักฐาน** — Hub-and-Spoke ใช้
   routing calls น้อยสุดและ coupling O(N) ซึ่งรองรับการวัดผล
   และการ debug จากจุดกลางจุดเดียวตลอดงานวิจัย

## 5.2 อภิปราย

### 5.2.1 การแลกเปลี่ยนระหว่างความแม่นยำและความซับซ้อนของ prompt

การ ablation (บท 4.1) ชี้ว่าแต่ละ feature มีต้นทุนต่างกัน:
+history ให้ประโยชน์มหาศาลใน multi-turn (+0.200) แต่ทำให้ค่า
confidence เฉลี่ยเพิ่มเป็นสองเท่า (3.93 → 9.12 ในมาตรวัด logit)
ขณะที่ +symbol hint และ +threshold ให้ประโยชน์น้อยกว่าและบาง
กรณีตีความเป็น "กำกวม" มากเกินไป (clarify 5.2%) ผลนี้
ตอบคำถามวิจัยว่า prompt engineering ที่มีเหตุผลเฉพาะโดเมน
(การให้บริบทบทสนทนา) สำคัญกว่าการเพิ่มเทคนิคทั่วไป
และที่สำคัญ — **จุดอ่อนที่เจอจริง (โมเดลหลุดจากบทบาทเมื่อมี
history) ถูกแก้ด้วยการปรับ prompt โครงสร้าง** (วาง instruction
หลังประวัติ ใช้หลัก recency) แสดงว่าการวัดผลแบบ ablation
ช่วยให้การแก้ไขตั้งอยู่บนหลักฐาน ไม่ใช่การเดา

### 5.2.2 การจัดการข้อจำกัดของ evaluator ในบทบาทตรงข้าม

ผล hallucination (บท 4.2) แสดงกรณีที่น่าสนใจเชิงระเบียบวิธี:
การตรวจด้วยกติกา regex ให้ผล 0.70 แต่เมื่ออ่านเนื้อหาจริง
คำตอบหลักถูก 10/10 — ตัวเลขที่ถูกจับมาเป็น "อวดความรู้"
ล้วนเป็นค่ากลางในการอธิบายที่ถูกต้อง (เช่นเพดานรวมกองทุน
500,000) งานวิจัยนี้เลือก**รายงานทั้งสองมุมอย่างโปร่งใส**
แทนการปรับ dataset ให้สวยงาม เพราะเป็นตัวอย่างที่ชัดว่า
การวัด hallucination อัตโนมัติด้วย regex มีขอบเขตจำกัด และ
การ "แก้ผล" ให้สวยโดยไม่ยืนยันตัวจริงคือความเสี่ยงทาง
วิชาการที่ควรเลี่ยง

### 5.2.3 ทำไม Hub-and-Spoke ยังเป็นตัวเลือกที่ถูกต้อง

ผลบท 4.4 ยืนยันตรรกะการออกแบบบทที่ 3: latency ส่วนใหญ่ถูก
จำกัดด้วยเวลาทำงานของ agent (~20 s) ซึ่งเหมือนกันทุก
สถาปัตยกรรม ดังนั้นเกณฑ์ตัดสินที่แท้จริงคือต้นทุน routing
(1.0 vs 1.8/2.0 calls) และความซับซ้อนเชิงโครงสร้าง (coupling
O(N) vs O(N²)) โดยเฉพาะเมื่อจำนวน agent เพิ่มขึ้น ข้อจำกัด
SPOF ของ Router ถูกชดเชยด้วยกลไก fallback เมื่อ confidence
ต่ำและมี misroute analysis ตรวจสอบย้อนหลังได้จาก log กลาง
ซึ่งเป็นเหตุผลที่วัดได้จริงในงานนี้ (ต่างจากการกระจายจุด
พังแบบ P2P ที่ trace ยาก)

## 5.3 ข้อจำกัดของงาน

### (ก) ข้อจำกัดเชิงข้อมูลและ ground truth

- **Datasets เป็นข้อมูลสังเคราะห์** — routing 45 เคส, ภาษี 20
  เคส, RAG 39 queries ทั้งหมดออกแบบโดยผู้วิจัย แม้ครอบคลุม
  intent ครบทุกประเภท แต่ไม่ได้มาจากผู้ใช้จริงในขนาดเชิง
  สถิติ ผลที่ได้จึงเป็นการพิสูจน์ความสามารถของระบบ ไม่ใช่
 การวัดความพึงพอใจผู้ใช้จริง
- **Ground truth เข้มงวดเกินจริงในบางมุม** — เคสภาษีที่มี
  เงื่อนไขเกินเพดาน (tax_acc_019) คาดหวัง scenario เดียวจาก
  2 กรณีที่ agent ตอบอย่างถูกต้องทั้งคู่ และ forbidden-pattern
  ของ hallucination จับตัวเลขในบริบทอธิบายที่ถูกต้อง 3 เคส

### (ข) ข้อจำกัดเชิงวิธีการ

- **Ablation เฉพาะโมเดลเดียว (Phase 1)** — ทั้ง 810 calls รัน
  บน minimax-m3 เท่านั้น การเชื่อมโยงผลไปยังโมเดลอื่นเป็น
  การอ้างอิงการเปรียบเทียบ routing แบบมีเงื่อนไข (0.94 vs 0.91)
  ไม่ใช่ ablation สมบูรณ์ — ถูกจัดเป็นงานต่อเนื่อง (Phase 2)
- **การประเมิน RAG ทำที่ระดับไฟล์** — Recall@3 วัดที่
  document-level (35 เป้าหมายจาก 1,586 chunks) ยังไม่วัด
  คุณภาพคำตอบสุดท้ายแบบ end-to-end ของ RAG
- **สถาปัตยกรรมที่เทียบในบท 4.4 ถูกจำลอง** — เฉพาะ
  Hub-and-Spoke ที่รันจริงแบบ end-to-end ฝั่ง P2P/Hierarchical
  จำลองเฉพาะกลไก routing ตัวเลข latency ของทางเลือกจึง
  ไม่รวม overhead การ implement จริงทั้งหมด

### (ค) ข้อจำกัดเชิงระบบ

- **Latency ~20 วินาทีต่อ query** บน minimax-m3 ยังสูงสำหรับ
  การแชทสด การเลือกโมเดลที่เร็วกว่า (เช่น gemini-3.5-flash
  ที่ทดสอบข้ามโมเดลแล้ว) พร้อมสำหรับสลับใช้ได้ทันที
  เพราะระบบ abstract provider ผ่าน configuration
- **การขึ้นกับผู้ให้บริการภายนอก** — ทั้ง LLM API, yfinance
  และ ChromaDB เป็น dependency ภายนอก ไม่มีเฟลบแบ็ค
  เชิงเต็มรูปเมื่อ network ล่ม (นอกจาก clarify fallback)
- **การวัด hallucination ยังอยู่ที่ระดับกติกา** — ตามข้อ
  5.2.2 ยังไม่ได้ใช้ LLM-as-judge ตรวจความจริงเชิงเนื้อหา

## 5.4 งานวิจัยต่อยอดที่เป็นไปได้

1. **Ablation ข้ามโมเดล (Phase 2)** — รันชุด 810 calls เดิมบน
   gemini-3.5-flash เพื่อตรวจว่าการแสดงออกของ history feature
   ขึ้นกับโมเดลหรือไม่ (เครื่องมือพร้อมใช้: `--ablation-models`)
2. **Evaluator ระดับประโยค** — ปรับ forbidden-pattern ให้จับ
   เฉพาะประโยคคำตอบหลัก แก้ข้อจำกัดในข้อ 5.3 (ก)
3. **ประเมิน end-to-end ของ RAG** — วัดคุณภาพคำตอบหลัง
   ใส่บริบท ไม่ใช่แค่คุณภาพการดึงเอกสาร
4. **การวัดผลจากผู้ใช้จริง** — ผ่าน LINE chatbot เพื่อวัด
   อัตราการ re-ask / clarify ในที่จริง ซึ่งเป็นตัวชี้วัดที่
   ablation ทำแทนไม่ได้

## 5.5 บทสรุป

งานวิจัยนี้พิสูจน์ได้ว่าระบบ multi-agent สำหรับการเงินส่วนบุคคล
ภาษาไทยที่ออกแบบด้วยหลัก evidence-driven (วัดผลทุกการตัดสินใจ
เชิงสถาปัตยกรรม) สามารถทำงานได้จริงในระดับ production:
จำแนกเจตนาถูกต้อง 0.94–1.00 คำนวณภาษีถูกต้อง 95% ค้นคืน
ความรู้ Recall@3 0.897 พร้อมจัดการข้อจำกัดที่พบอย่างโปร่งใส
คุณค่าเชิงวิธีการที่ชัดที่สุดคือระเบียบวิธี "ablation-first"
— การพิสูจน์ทุก feature ด้วยการวัดผลก่อนเปิดใช้ใน production
ซึ่งจับข้อผิดพลาดเชิงพรอมต์ที่ไม่มีการวัดผลจะมองไม่เห็น
ตลอดจนถึงการรายงานผลตรวจสอบย้อนหลังได้ทั้งหมด
