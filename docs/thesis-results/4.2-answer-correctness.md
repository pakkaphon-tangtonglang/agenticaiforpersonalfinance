# 4.2 ประสิทธิภาพด้านความถูกต้องของคำตอบ (Answer Correctness)

> เอกสารร่างสำหรับบทที่ 4 ของวิทยานิพนธ์ — ตัวเลขทั้งหมดมาจากผลรันจริง
> อ้างอิง artifact ท้ายเอกสาร ประเมินด้วยโมเดล production `minimax-m3`
> ผ่าน Ollama Cloud (ตาม configuration เดียวกับบท 4.1 และ 4.4)

## 4.2.1 การออกแบบการทดลอง

ความถูกต้องของคำตอบวัดด้วย 2 มิติ ตามเกณฑ์ในเค้าโครง:

| มิตริก | วิธีประเมิน | ความเป็นกลาง |
|---|---|---|
| **Tax accuracy** | เทียบภาษีที่ agent คำนวณกับ ground truth ที่คำนวณด้วยโมดูลภาษี (deterministic) ยอมรับความคลาดเคลื่อน ±tolerance | deterministic ไม่ใช้ LLM ตัดสิน |
| **Hallucination compliance** | ตรวจคำตอบตาม `known_facts` + `forbidden_patterns` ต่อเคส | rule-based (regex ตรวจเลขห้ามกล่าวอวด) |

**ชุดข้อมูล** — 20 เคสภาษี (เงินได้ 0–3 ล้านบาท, ค่าลดหย่อนรวม
RMF/SSF/ประกันสังคม/ค่าฝึกอบรม ฯลฯ) และ 10 เคสตรวจอาการ
hallucination (ตัวเลขกฎหมายภาษีที่มักถูกอ้างผิด) โดยทุกเคสรัน
end-to-end ผ่าน Tax Agent จริง (LLM + tools) เช่นเดียวกับการใช้งานจริง

## 4.2.1 ผลลัพธ์ภาพรวม

| มิตริก | ค่า |
|---|---|
| Tax accuracy (within tolerance) | **95.00%** (19/20) |
| Mean absolute error | **3,000 THB** (ต่อเคสเฉลี่ยทั้ง 20) |
| Latency เฉลี่ยต่อเคส | 10.72 วินาที |
| Hallucination compliance (raw, ตาม regex) | **70.00%** (7/10) |

## 4.2.3 การวิเคราะห์ผล

### (ก) Tax accuracy — 95% โดยผิดเพียงเคสที่มีเงื่อนไขซับซ้อนพิเศษ

19 เคสจาก 20 คำนวณภาษีตรงกับ ground truth ภายใน tolerance —
ครอบคลุมตั้งแต่เงินได้น้อย (ภาษี 0) ถึงรายได้ 3 ล้านบาทพร้อม
ค่าลดหย่อนหลายประเภท MAE 3,000 THB ต่อเคสเฉลี่ย ถือว่าต่ำมาก
เมื่อเทียบกับมาตราส่วนรายได้ (ค่าเฉลี่ยรายได้ใน dataset ~9 แสนบาท)

เคสที่ผิด (`tax_acc_019`: รายได้ 3,000,000 บาท + ลดหย่อน 60,000 +
RMF 500,000 + SSF 200,000) มีลักษณะพิเศษ 3 ประการ:

1. RMF + SSF รวม 700,000 บาท **เกินเพดานกองทุนเกษียณรวม
   500,000 บาท** — agent จึงตอบด้วย **2 กรณีเปรียบเทียบ** (ตามที่
   ผู้ใช้แจ้ง vs ตามเพดานกฎหมาย) ซึ่งเป็นพฤติกรรมที่ดีต่อผู้ใช้
2. ตัวตรวจ (extractor) เลือกตัวเลขจากส่วนสรุป "กรณีทำตามกฎหมาย"
   (467,000) แต่ dataset คาดหวังกรณีตามที่ผู้ใช้แจ้ง (407,000)
   — เกิดความคลาดเคลื่อน 60,000 THB จากการจับคู่ scenario
   ไม่ตรงกัน มากกว่าการคำนวณผิดโดยตรง
3. คำตอบถูกต้องตามเงื่อนไขหนึ่งในสองอยู่แล้วในข้อความเดียว

ข้อเสนอ: กรณีเงินลดหย่อนเกินเพดานคือ **edge case ที่ควรกำหนด
expected ให้ชัดเจนว่าอ้างอิง scenario ใด** และ extractor ควรเลือก
ตัวเลขจาก scenario ที่ agent ระบุว่าเป็นคำตอบหลัก

### (ข) Hallucination — ควรอ่านผล raw คู่กับการวิเคราะห์เชิงเนื้อหา

ผล raw ตามกติกา regex คือ 70% (7/10) แต่เมื่อตรวจคำตอบจริงของ
3 เคสที่ถูก flag พบว่า **คำตอบหลักของ agent ถูกต้องทั้งหมด**
สอดคล้องกับ knowledge base ของระบบเอง ตัวเลขที่ถูกจับเป็น
"ต้องห้าม" ล้วนปรากฏใน**บริบทที่ถูกต้องตามกฎหมาย**:

| เคส | คำตอบหลัก (ตรง KB) | ตัวเลขที่ถูก flag | บริบทจริงของตัวเลขนั้น |
|---|---|---|---|
| hal_002 (RMF) | "สูงสุด 500,000 (30%)" ✓ | 600,000 | ค่ากลางในตารางตัวอย่าง (2,000,000×30%) ที่ agent ชี้ว่า "ติดเพดาน 500,000" |
| hal_007 (ประกันสังคม) | "สูงสุด 9,000/ปี" ✓ | 15,000 | เพดานค่าจ้างเพื่อคำนวณเงินสมทบ 15,000 บาท/เดือน (ข้อเท็จจริงจริง) ไม่ใช่ค่าลดหย่อน |
| hal_009 (SSF) | "สูงสุด 200,000" ✓ | 500,000 | เพดานรวมกองทุนเกษียณทุกประเภท 500,000 บาท (คำเตือนที่ถูกต้อง) |

**ข้อสรุปสองชั้น:**

- ในแง่ **ความถูกต้องของข้อเท็จจริง** agent ไม่อวดตัวเลขเลย
  (10/10 เคสให้ตัวเลขหลักตรงกับ knowledge base)
- ในแง่ **เครื่องมือวัด** การตรวจด้วย forbidden-pattern (regex)
  แบบตรงตัวมีข้อจำกัด: ไม่แยกว่าตัวเลขถูกใช้เป็น "คำตอบ" หรือ
  "บริบทอธิบาย" การพัฒนาต่อคือจำกัดขอบเขตการจับคู่ให้ตรง
  ประโยคคำตอบหลัก ซึ่งเป็นข้อเสนอแนะเชิงระบบชัดเจนสำหรับ
  บทที่ 5 (ข้อจำกัดของงาน)

การรายงานตัวเลขทั้งสองมุม (0.70 raw / 1.00 headline) ทำให้
ผู้อ่านเห็นพฤติกรรมจริงของระบบครบถ้วน และแสดงให้เห็นว่า
การตรวจ hallucination อัตโนมัติด้วยกติกามีความเข้มงวด
เกินจริงใน 3 กรณี แทนที่เป็นข้อบกพร่องของโมเดล

## 4.2.4 สรุป

- Tax accuracy **95% (19/20)**, MAE **3,000 THB** — การคำนวณภาษี
  ที่ซับซ้อนสูงสุดถึง 5 ประเภทค่าลดหย่อนถูกต้องเกือบทั้งหมด
- ความผิดพลาดทั้งหมดกระจุกอยู่ที่ edge case เพดานรวมกองทุน
  เกษียณ + คำตอบ 2 กรณี ซึ่งเป็นข้อจำกัดของ extraction
  มากกว่าความสามารถของ agent
- Hallucination: คำตอบหลักถูกต้อง 10/10 ผล raw 0.70 สะท้อน
  ความเข้มงวดของ regex evaluator มากกว่าพฤติกรรมจริงของ
  โมเดล — และเป็นข้อจำกัดที่ระบุชัดเจนในข้อจำกัดของงาน
