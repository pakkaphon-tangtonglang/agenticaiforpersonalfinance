# 4.4 การเปรียบเทียบสถาปัตยกรรม Multi-Agent

> เอกสารร่างสำหรับบทที่ 4 ของวิทยานิพนธ์ — เนื้อหาภาษาไทยพร้อมตารางที่คัดลอกไป
> Word/Google Docs ได้ทันที ตัวเลขทั้งหมดมาจากผลรันจริง อ้างอิง artifact ท้ายเอกสาร

## 4.4.1 การออกแบบการทดลอง

ระบบที่พัฒนาเลือกสถาปัตยกรรม **Hub-and-Spoke** (Router กลางพร้อม
6 specialist agents) การทดสอบนี้วัดข้ออ้างเชิงประจักษ์ของการเลือกนั้น
โดยเทียบกับสถาปัตยกรรมทางเลือกอีก 2 แบบที่พบบ่อยในงาน multi-agent:

| สถาปัตยกรรม | กลไก routing | ลักษณะ |
|---|---|---|
| **Hub-and-Spoke** (ระบบนี้) | Router จำแนก 1 ครั้ง → ส่งต่อ 1 agent | จุดเดียวกลาง, coupling O(N) |
| Peer-to-Peer (P2P) | จำลอง agent โยงงานข้ามกัน (hops) | coupling O(N²), ความล่าช้าสะสมต่อ hop |
| Hierarchical | จำลอง macro-classifier 2 ชั้น | 2 routing LLM calls ต่อ query |

**โปรโตคอล** — 5 queries ภาษาไทยชุดเดียวกัน (ภาษี / ค่าใช้จ่าย / หุ้น /
วางแผน / รายงาน) ผ่านแต่ละสถาปัตยกรรม: ฝั่ง Hub-and-Spoke รัน
end-to-end จริงผ่าน `orchestrate_query` (routing + agent ตอบจริงด้วย
`minimax-m3`) ส่วน P2P และ Hierarchical จำลองเฉพาะกลไก routing/hops
บนโมเดลเดียวกันเพื่อเทียบโครงสร้าง ตัวชี้วัดคือ latency, จำนวน routing
LLM calls, จำนวน hops และความยุ่งเหยิงเชิงโครงสร้าง (coupling)

## 4.4.2 ผลลัพธ์ภาพรวม

| เมตริก | Peer-to-Peer | Hierarchical | Hub-and-Spoke |
|---|---|---|---|
| Routing LLM calls / query | 1.8 | 2.0 | **1.0** |
| Coupling (N = 6 agents) | 15 connections | 8 connections | **6 connections** |
| อัตราการเติบโตของ coupling | O(N²) | O(N + levels) | **O(N)** |
| Latency เฉลี่ย (ms) | 20,208 | 20,239 | 20,795 |
| เพิ่ม agent ใหม่ต้องแก้ | ทุก agent | 2 router | **router เดียว** |
| จุดล้มเหลว | กระจาย (ตรวจยาก) | router หลัก | router หลัก |

## 4.4.3 การวิเคราะห์ผล

### (ก) Latency ใกล้เคียงกัน เพราะถูกจำกัดด้วยเวลาของ agent ไม่ใช่ routing

Latency เฉลี่ยของทั้งสามแบบอยู่ราว 20–21 วินาที ต่างกันเพียง ~3% —
เพราะเวลาส่วนใหญ่ใช้กับการทำงานของ specialist agent (เรียก LLM +
tools จริง) ซึ่งเหมือนกันทุกสถาปัตยกรรม การตีความจึงต้องชี้ที่
**ต้นทุน routing และโครงสร้าง** มากกว่า latency ดิบ อย่างไรก็ตาม
แบบ P2P มีการสะสม latency ต่อ hop (เช่น query ภาษี 30,670 ms หรือ
+56% จากการแลกเปลี่ยนระหว่าง agent 2 ขั้น) ซึ่งจะโตเร็วขึ้นตามจำนวน
hops เมื่อระบบซับซ้อนขึ้น

### (ข) Routing LLM calls — Hub-and-Spoke จ่าย API เพียงครั้งเดียว

ข้อได้เปรียบที่ชัดที่สุด: ทุก query ผ่าน **1 routing LLM call** เทียบกับ
1.8 (P2P) และ 2.0 (Hierarchical) หมายความว่าต้นทุน API ฝั่ง routing
ต่ำกว่า ~2 เท่า และพื้นผิวการพังลดลง (failure surface) — การจำแนกผิด
และความล่าช้าจาก network เกิดต่อ query น้อยลงเท่าตัว

### (ค) Coupling และการขยายระบบ

ที่ N = 6 agents: P2P ต้องเชื่อม 15 เส้นทาง O(N²), Hierarchical
8 เส้นทาง แต่ Hub-and-Spoke เพียง 6 เส้น (O(N)) เมื่อเพิ่ม agent
ที่ 7 P2P จะเพิ่ม 6 connections (21) ขณะที่ Hub-and-Spoke เพิ่มเพียง
เส้นทางเดียว นอกจากนี้การ debug ง่ายกว่าชัดเจน: ทุก query ผ่านจุด
เดียว (Router) ทำให้ trace intent/latency/error ได้จาก log กลางจุดเดียว
ซึ่งสอดคล้องกับวิธีที่บท 4.1–4.3 วัดผลจาก log กลาง

### (ค) ข้อจำกัดที่ยอมรับได้

Hub-and-Spoke มี single point of failure ที่ Router — แต่ Router ของ
ระบบนี้ถูกออกแบบมาให้ fail gracefully (ผลจากบท 4.1: misroute ถูกจัด
เป็นกรณีกำกวมเชิงภาษา และมี fallback `clarify` เมื่อ confidence ต่ำ)
การวัดในบทนี้จึงถือว่า SPOF เป็น trade-off ที่ยอมรับได้เมื่อแลกกับ
routing calls ที่น้อยที่สุดและ coupling ที่ต่ำที่สุด

## 4.4.4 สรุป

- Hub-and-Spoke ใช้ routing LLM calls **1.0** ต่อ query — น้อยกว่า
  P2P (1.8) และ Hierarchical (2.0) ราว 2 เท่า
- Coupling ต่ำที่สุดและโตช้าที่สุด O(N) — 6 เส้นทางที่ N = 6 เทียบกับ
  15 (P2P) และ 8 (Hierarchical)
- Latency เฉลี่ยรวมเท่ากัน (~20 s) เพราะถูกจำกัดด้วยเวลา agent จริง
  แต่ P2P แสดง penalty ต่อ hop ชัดเจนในบาง query
- ผลลัพธ์สนับสนุนการเลือก Hub-and-Spoke ตามที่ออกแบบไว้ในบทที่ 3
