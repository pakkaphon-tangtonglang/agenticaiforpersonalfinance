# 4.1 ความแม่นยำของ Router และการวิเคราะห์ Ablation

> เอกสารร่างสำหรับบทที่ 4 ของวิทยานิพนธ์ — เนื้อหาภาษาไทยพร้อมตารางที่คัดลอกไป
> Word/Google Docs ได้ทันที ตัวเลขทั้งหมดมาจากผลรันจริง อ้างอิง artifact ท้ายเอกสาร

## 4.1.1 การออกแบบการทดลอง

Router เป็นองค์ประกอบแรกที่ตัดสินใจแทนผู้ใช้ทั้งระบบ — ถ้าจำแนก intent
ผิด คำถามจะไปถึง agent ที่ไม่เหมาะสม และคำตอบที่เหลือทั้งหมดจะผิดเป้าไปด้วย
การทดสอบนี้จึงมีสองส่วน: (1) วัดความแม่นยำพื้นฐานของ router บนชุดทดสอบ
single-turn (2) **ablation study** — ปิด/เปิดคุณสมบัติทีละอย่างเพื่อวัด
marginal effect ของแต่ละ feature ต่อความแม่นยำ

**ชุดทดสอบ 2 ชุด**

| ชุด | จำนวน | ลักษณะ | กรณีครอบคลุม |
|---|---|---|---|
| base | 35 เคส | คำถาม single-turn ตั้งใจให้ตัดสินใจจากข้อความเดียว | tax 6, expense 6, asset_monitoring 6, planning 5, recommendation 4, report 3, general 2, unknown 3 |
| history | 10 เคส | บทสนทนาหลายรอบ — ข้อความสุดท้ายออกแบบให้**กำกวมจนแก้ไม่ได้ถ้าไม่มีประวัติ** (ใช้คำสรรพนาม "อันนั้น/อันนี้", วลีเฉพาะที่, ข้อมูลที่หายไป) | asset_monitoring 2, expense 2, tax 2, planning 1, recommendation 1, report 1, general 1 |

การออกแบบชุด history ให้ query สุดท้ายกำกวมโดยเจตนา (เช่น "แล้ววันนี้ขึ้น
หรือลงเปล่า" หลังถามราคาหุ้น PTT) จึงเป็นการวัด**ประโยชน์จริง**ของการใส่
chat history เข้าสู่ context ไม่ใช่เพียงการยืนยันว่าระบบทำงานได้กับข้อความ
ปกติ

**ตัวแปรในการทดลอง (Ablation Variants)** — ผู้วิจัยกำหนดการตั้งค่า 6 แบบ
โดย 5 แบบแรกเปิด feature เดียวจากค่าเริ่มต้นว่าง และแบบสุดท้ายเป็น
configuration เต็มของ production:

| Variant | few-shot | history | symbol hint | threshold | ความหมาย |
|---|---|---|---|---|---|
| baseline | – | – | – | – | จำแนกจากข้อความเดียว ไม่มีตัวช่วย |
| +few_shot | ✓ | – | – | – | ใส่ตัวอย่าง JSON 9 รูปแบบใน system prompt |
| +history | – | ✓ | – | – | แนบบทสนทนาล่าสุดเป็นบริบท |
| +symbol | – | – | ✓ | – | ค้นหา ticker จาก Yahoo Finance แล้วแนบ hint |
| +threshold | – | – | – | ✓ | ความมั่นใจ < 0.6 จะตอบ clarify แทน |
| full (DEFAULT) | ✓ | ✓ | ✓ | – | configuration ของ production |

**โปรโตคอลการรัน**

| พารามิเตอร์ | ค่า |
|---|---|
| โมเดล | `minimax-m3` ผ่าน Ollama Cloud API (Phase 1) |
| จำนวนรอบ | 3 รอบต่อ (variant, เคส) เพื่อควบคุมความแปรปรวน |
| จำนวนการเรียก LLM ทั้งหมด | 6 variants × 45 เคส × 3 รอบ = **810 calls** |
| เกณฑ์การตัดสิน | ถูกต้องเมื่อ intent ตรงกับที่กำกับ (เคส history ที่กำกับให้ clarify ต้องได้ clarify) |
| การจัดเก็บ | raw log แบบ JSONL ที่ resume ได้ (ทุก call บันทึก intent, confidence, latency) |
| Latency เฉลี่ยต่อ call | 2.3–3.9 วินาที แล้วแต่ variant |

ข้อสังเกต: ผลลัพธ์รายงานแยกกลุ่มเคส base และ history เพื่อให้เห็นว่าแต่ละ
feature ช่วย (หรือกระทบ) บทบาทใดบ้าง ทั้งนี้ accuracy บนชุด base 35 เคส
ของ baseline (0.943) สอดคล้องกับผลการประเมิน routing ก่อนหน้า (0.94)
ซึ่งเป็นการยืนยันความ consistent ของชุดทดสอบ

## 4.1.2 ผลลัพธ์ภาพรวม

| Variant | base acc (mean ± std) | history acc (mean ± std) | clarify rate | latency (s) |
|---|---|---|---|---|
| baseline | 0.943 ± 0.000 | 0.733 ± 0.058 | 0.000 | 3.93 |
| +few_shot | 0.924 ± 0.016 | 0.833 ± 0.058 | 0.000 | 2.71 |
| +history | 0.943 ± 0.000 | **0.933 ± 0.058** | 0.000 | 9.12 |
| +symbol | 0.943 ± 0.000 | 0.800 ± 0.100 | 0.000 | 2.56 |
| +threshold | 0.943 ± 0.000 | 0.667 ± 0.115 | 0.052 | 2.29 |
| full (production) | 0.905 ± 0.016 | **1.000 ± 0.000** | 0.000 | 3.11 |

## 4.1.3 การวิเคราะห์ผล

### (ก) Chat history คือ feature ที่มี marginal effect สูงสุด

การเพิ่ม chat history เพียงอย่างเดียวเพิ่มความแม่นยำบนบทสนทนาหลายรอบ
จาก 0.733 เป็น **0.933 (+0.20)** โดยไม่กระทบความแม่นยำบนชุด base
(0.943 เท่าเดิม) ซึ่งตอบคำถามหลักของการออกแบบ: ประวัติการสนทนาจำเป็น
เพื่อให้ router เข้าใจข้อความอ้างอิงถึงบริบทเดิม ("อันนั้น", "แบบนี้",
"อีก 120 ด้วย")

### (ข) Feature ทั้งหมดทำงานเสริมกันใน configuration เต็ม

configuration เต็ม (few-shot + history + symbol hint) ได้ accuracy
**1.000 ± 0.000** บนชุด history ครบทั้ง 3 รอบ — สูงกว่า +history แบบ
โดด ๆ (0.933) แสดงว่าตัวอย่าง few-shot ช่วยยืนยันรูปแบบ JSON output
ในบริบท multi-turn ที่มีข้อความมากขึ้น ส่วนบนชุด base configuration เต็ม
ได้ 0.905 ต่ำกว่า baseline เล็กน้อย (1 เคสใน 3 รอบเปลี่ยนคำตอบ) ซึ่ง
ภายในช่วงความแปรปรวนที่ยอมรับได้ (±0.05) ของ LLM

### (ค) Confidence threshold มี trade-off ชัดเจน

การเปิด threshold 0.6 ทำให้ accuracy บนชุด history **ลดลง** (0.667) และ
เกิด clarify 5.2% — เหตุผลคือเคสที่กำกวมจริงจะได้ confidence ต่ำกว่า
threshold และถูกถามกลับ ในมุมระบบจริงถือเป็นพฤติกรรมที่พึงประสงค์
(ถามกลับดีกว่าส่งต่อผิด agent) แต่ในการวัด accuracy อย่างเดียวจึงปรากฏ
เป็นค่าลบ การแปลผลต้องอ่าน clarify rate ควบคู่กันเสมอ

### (ง) ตรวจสอบความถูกต้องของ feature implementation (prompt-mode QA)

รันครั้งแรกพบผลผิดปกติรุนแรง: variant +history มี accuracy บนชุด history
เพียง 0.133 และโมเดลตอบ `unknown` พร้อม confidence 0 ใน 8 จาก 10 เคส
การตรวจสอบระดับ raw response พบว่า**โมเดลหลุดจากบทบาท classifier** —
เมื่อเห็นข้อความ assistant ในประวัติ โมเดลกลับไปตอบคำถามแบบผู้ช่วย
("หุ้น PTT วันนี้ลดลง 0.75 บาท...") แทนที่จะส่ง JSON การจำแนก สาเหตุคือ
system prompt เดิมไม่มีคำสั่งเกี่ยวกับการใช้ประวัติการสนทนาเลย

ผู้วิจัยแก้ไขโดยแทรก SystemMessage ปิดท้ายบล็อกประวัติว่า "ประวัติการสนทนา
ใช้เป็นบริบทอย่างเดียว จำแนกเฉพาะข้อความสุดท้ายของผู้ใช้ และตอบเป็น JSON
เท่านั้น" (commit `9004652`) พร้อม unit tests 4 กรณี แล้วรันซ้ำเฉพาะ
variant ที่ใช้ history (+history และ full รวม 270 calls) ผลเปลี่ยนจาก
0.133 → **0.933** และ 0.233 → **1.000** ตามลำดับ

ข้อค้นพบนี้มีนัยสองด้าน: (1) เชิงวิศวกรรม — การแนบประวัติสนทนากับ LLM
ที่ทำงานแบบ structured output ต้องมี role instruction กำกับเสมอ มิฉะนั้น
โมเดลจะรับ role ของผู้ตอบสนทนา (2) เชิงระเบียบวิธี — ผลลัพธ์ ablation
ที่วัดครั้งเดียวอาจสะท้อนข้อบกพร่องของ implementation มากกว่าคุณค่าของ
feature จึงต้องตรวจสอบ raw response ก่อนสรุป ผลลัพธ์ในตารางทั้งหมดมาจาก
implementation ที่ผ่านการตรวจสอบนี้แล้ว

### (ง) ผลลัพธ์ที่คาดหวังกับ production

โมเดล production ของระบบ (full configuration) จึงได้ประโยชน์เต็มที่จาก
history บนบทสนทนาจริง (1.000) ขณะที่คงความแม่นยำ 0.905 บนคำถามเดี่ยว
และกรณี misroute ที่ทราบก่อนหน้า ("ควรลงทุนอะไรดี") ยังคงเป็นข้อจำกัด
ของความกำกวมเชิงภาษา ไม่ใช่ข้อบกพร่องของ feature ใด

## 4.1.4 สรุป

- Router แม่นยำ **0.943** บนคำถาม single-turn และ **1.000** บน
  multi-turn เมื่อเปิดครบทุก feature
- **Marginal effect ของ chat history สูงสุด** (+0.20 บน multi-turn)
  รองลงมาคือ few-shot examples (+0.10) และ symbol hint (+0.07)
- การเปิด confidence threshold เดี่ยว ๆ ลด accuracy แต่เพิ่มการถามกลับ
  (clarify 5.2%) — เหมาะกับระบบที่ให้น้ำหนักความปลอดภัยมากกว่า coverage
- ผลทั้งหมดจาก 3 rounds มีค่า std ต่ำ (≤ 0.115) แสดงว่าโมเดลมีความ
  น่าเชื่อถือเชิงสถิติพอสำหรับข้อสรุปที่รายงาน
